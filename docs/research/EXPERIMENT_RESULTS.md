# Matching-Research Experiment Results

## Run record

This report records the output generated by `MatchingBenchmarkTest` on 2026-10-19. The raw, reproducible artifacts are:

- `docs/research/results/matching_benchmark_summary.csv`
- `docs/research/results/matching_benchmark_queries.csv`
- `docs/research/results/matching_benchmark_plot.svg`

The test was run on Windows 11 x64 with Oracle JDK 21.0.12 and Maven 3.9.16. The benchmark is a single JVM test using the fixed 20-query / 80-candidate corpus and the deterministic query-order seed `20261019`.

Each configuration uses 5 unrecorded warm-up passes and 15 measured passes. A pass ranks all 20 queries. Dataset loading, index construction, metric calculation, CSV writing, and SVG writing are outside the timed interval. The timed rank result is consumed through a volatile checksum so it cannot be discarded as unused work. Runtime figures are therefore query-set ranking times for this machine and run, not general latency claims.

## Protocol

All methods use the same labels and a score threshold of `0.60` for precision, recall, and F1:

```text
precision = TP / (TP + FP)
recall    = TP / (TP + FN)
F1        = 2 × precision × recall / (precision + recall)
```

`Hit@1`, `Hit@3`, and `Hit@5` are calculated from the raw deterministic ranking before thresholding. They are reported only over the 17 queries that have a known true item; the three no-match queries are excluded from the Hit@k denominator. A no-match query that returns an item at or above `0.60` contributes a false positive to precision/F1.

The methods are:

| Method | Implementation |
|---|---|
| Exact filtering | `MatchingBenchmarkTest.exactFiltering`: category, color, location, and unique text-token sets must all match. |
| Weighted full scan | `weightedFullScan` plus `SimilarityScorer.score`: all 80 reports, Jaccard text. |
| Indexed weighted ranking | `indexedWeightedRanking` plus `CandidateIndex`: `FoundItemHashTable` limits work to the same category and `FoundItemTrie` supplies exact token-intersection counts. It preserves the scorer's score and candidate-ID tie rule. |
| Enhanced TF-IDF cosine | `enhancedTextRanking` with `TextSimilarityStrategies.tfIdfCosine`; only the text component changes. |
| Enhanced Levenshtein | `enhancedTextRanking` with `TextSimilarityStrategies.levenshteinTokenFuzzy`; only the text component changes. |

The 35/30/35, 25/25/50, and 20/30/50 rows change only the color/location/keyword weights. The corpus, labels, category gate, threshold, ordering, and measured environment remain fixed.

## What the numbers support

- Exact filtering was precise but missed 11 of the 17 true matches at the threshold (`R=0.353`, `F1=0.522`). It is not a suitable primary retrieval method on this corpus.
- With the 25/25/50 and 20/30/50 sets, weighted Jaccard achieved the best observed F1 (`1.000`). The indexed version had the same output quality because it preserves the baseline score, while examining 8 rather than 80 candidates on average. On this run its median was 6.596 ms (25/25/50) or 6.812 ms (20/30/50), versus 23.752 ms and 17.339 ms for the equivalent full scans.
- The noisy true positive `L13 → F18` illustrates the text/weight trade-off. At 35/30/35, standard Jaccard and TF-IDF did not clear the `0.60` threshold for it, while fuzzy Levenshtein did. At the two 50% keyword-weight settings, full scan and indexed Jaccard both recovered it.
- The hard no-match `L20 → F77` shows why a similarity score remains only a suggestion. Its matching category, color, location, and generic word `notebook` caused a counted false positive for the 35/30/35 full/indexed rows and for all fuzzy rows. TF-IDF also produced that false positive at the two 50% keyword-weight settings. These reports still require staff review; the benchmark does not authorize a claim.
- TF-IDF was slower on this unoptimized implementation (218.259–239.299 ms median) and did not improve the best weighted-Jaccard F1. Fuzzy text recovered the controlled typo under 35/30/35 but had F1 `0.971` because of the hard no-match false positive, and its 41.278–42.968 ms medians were slower than the indexed baseline.

## Limits and next steps

These measurements are reproducible for this manually authored, closed-world course dataset, but they are not evidence of production accuracy or production latency. The corpus is small, English-only, contains at most one true candidate per query, and explicitly labels 100 representative pairs while treating all other candidate pairs as negatives under the documented fixed identity map. A larger independently reviewed dataset, repeated runs on a controlled machine, and user/staff feedback would be needed before making stronger claims.
